# 功能 3：BLE 广播信道风险评估（feat/3-ble-risk）

> 本文件是阶段 3 的验收材料。mock 侧 8 个场景全跑过；实板侧在 COM56 上跑过两轮
> （45 s / 13262 帧），**实板所在房间的 2.4G 本身很忙**，这一点在下面第 6 节原样交代，
> 没有拿 mock 数字冒充实板数字。

## 1. 做了什么

`modes/ble_risk.py`（单文件，未动 `core/`、未动其它模块）：

- 扫 BLE 全部 40 个信道的频段：3 个广播信道 **2402 / 2426 / 2480 MHz** 各用一个窗中心对准，
  数据信道区 2404–2478 MHz 用 20 MHz 窗 / 15 MHz 步进重叠滑扫，共 **8 个窗**。
- 逐窗判「这次有没有信号」「这个信号是不是窄带凸起」，聚合成广播信道活动占空、
  窄带突出度、覆盖率，再算拥挤评分与风险类型。
- 输出：ASCII 表格（4 行：3 个广播信道 + 数据区）+ 结构化 `web_payload()` + 共存建议。

## 2. 扫描计划

| 常量 | 值 | 依据 |
| --- | --- | --- |
| `SCAN_BW_HZ` | 20 MHz | 与功能 1 同一套口径（20 MS/s 整窗有效通带） |
| `USABLE_HALF_HZ` | ±10 MHz | 同上，窗外 0 码不参与判读 |
| `SCAN_STEP_HZ` | 15 MHz | 相邻窗重叠 5 MHz，数据区不留空洞 |
| `DWELL_MS` | 100 | 20 MHz / 1024 bin ⇒ 19.5 kHz 分辨率 |
| 窗数 | 8（2402/2414/2426/2429/2444/2459/2468/2480） | 3 个广播信道**中心对准**（要干净的肩部）+ 数据区 5 窗 |

```bash
python -c "from modes.ble_risk import scan_plan; print([f'{hz/1e6:.0f}' for hz in scan_plan()])"
# ['2402', '2414', '2426', '2429', '2444', '2459', '2468', '2480']
```

**为什么广播信道必须中心对准**：判据要拿 ±4~8 MHz 的肩部当参照，窗偏了肩部就一侧出窗、
一侧撞上邻道，凸起量算不准（这是第一版被 mock 抓出来的）。

## 3. 判据三原则（每条都是踩坑换来的）

### ① 电平取 **p80**，不取中位数

BLE 是 2 MHz 通道里的短脉冲，**不铺满整个 2 MHz**。中位数会被「没有脉冲的那一半 bin」
拉回底噪，导致强 BLE 也读成安静。实测：`ble_crowded` 场景中位数口径给 37% 活动、
p80 口径给 100% 活动，后者与场景注入一致（3 台强 BLE 常开广播）。

### ② 窄带占比门槛 ≥ `NARROW_RATIO`(50%)

只判「比肩部高 8 dB」不够：WiFi 的 20 MHz 梯形斜坡扫过广播信道时，
**一侧肩部低、一侧肩部高**，通道电平照样比肩部高十几 dB，会被误判成窄带凸起。
所以要求窄带凸起量 **≥ 本次抬升的 50%**：

```
rise   = level_p80 - ref            # 相对本帧底噪抬了多少
prom   = level_p80 - shoulder_p80   # 比肩部高多少
hit    = rise > 12 dB  and  prom > 8 dB  and  prom >= 0.50 * rise
```

### ③ 肩部取左右**各自 max**，不合并

两侧不对称（正是 WiFi 信道边缘扫过广播信道的形态）时，把左右肩部先合并再取中位，
会让参照电平跳变、台面被低估 → 又把 WiFi 斜坡算成窄带凸起。取 `max(left, right)`
（`_p80` 后取大者）后，`wifi_suppress_ble` 的假凸起从 88% 掉到 0%。

## 4. 判决口径

```
风险评分 = 0.8 × 广播活动占空 × 100 + 0.2 × min(100, 数据区栅格占用/帧 ÷ 12 × 100)

宽带占用 ≥ 50%            → WiFi 压制型（宽带源把窄带凸起埋了，分辨不出来）
否则 广播活动 ≥ 30%       → 蓝牙设备密度型
否则 广播活动 ≥ 12% 且宽带 ≥ 25% → 混合型
否则                      → 无明显风险
无任何有效帧              → 无数据
```

- `宽带占用率` **在时间均值频谱上算**，不在单帧上算。实板单帧噪声底跨 bin 抖动很大
  （实测 p10≈20 / p50≈28 / p90≈41），固定门限 `p10+10` 会让 **37%** 的纯噪声 bin 越线，
  安静环境直接被判成「2.4G 全被占」。多帧取均值后抖动按 1/√N 收敛，剩下的抬升才是真占用。
- WiFi 共存判读用**双半宽**：测电平只取 ±9 MHz（`WIFI_MEASURE_HALF_HZ`，避开邻道泄漏），
  判重叠按 ±10 MHz 几何（`WIFI_SPAN_HALF_HZ`，20 MHz 信道真实占用）；
  「在用」的判据是 **18 MHz 窗口里 ≥50% 的频点高于本帧 p10+8 dB**，不是电平 ——
  窄带 BLE 脉冲能把 p80 顶起来但只占 2/18 ≈ 11%，用比例才分得开。
- `宽带占用 ≥ 90%` 时，「在用 WiFi 信道」与「共存冲突」表不再有分辨力，输出里会显式说明。

**边界（写在 `notes()` 里，每次产出都带上）**：

- 只评概率，**不做设备级归因**（看不出「几台什么设备」）。
- 功率码是相对 dB 码，**不是 dBm**，绝不换算成功率/场强。
- 单射频分时扫描，帧与帧之间有接收空档。

## 5. mock 8 场景实测（`--slices 32`，全部本机真跑）

```bash
cd examples/esp32c5-rf-monitor
for s in quiet ble_crowded wifi_suppress_ble mixed microwave wifi_busy unknown_cw video_58g; do
  echo "== $s"; python -m modes.ble_risk --scenario "$s" --slices 32 | sed -n '7,11p'
done
```

| 场景 | 风险类型 | 评分 | 宽带占用 | 广播活动 |
| --- | --- | --- | --- | --- |
| `quiet` | 无明显风险 | 4.9 | 0% | 0% |
| `ble_crowded` | **蓝牙设备密度型** | **82.7** | 15% | 100% |
| `wifi_suppress_ble` | **WiFi 压制型** | 23.8 | 85% | 0% |
| `mixed` | WiFi 压制型 | 42.8 | 95% | 9% |
| `microwave` | WiFi 压制型（宽带源，非 WiFi 也归此档） | 31.7 | 66% | 9% |
| `wifi_busy` | WiFi 压制型 | 21.2 | 77% | 0% |
| `unknown_cw` | 无明显风险 | 19.3 | 31% | 0% |
| `video_58g` | 无明显风险（5.8G，不在 2.4G 判决内） | 4.8 | 0% | 0% |

任务书的两个硬判据：

- `ble_crowded` 评分 82.7 **>** `quiet` 4.9（差 77.8，测试里断言「差 > 30」）✅
- `wifi_suppress_ble` 判「WiFi 压制型」✅

## 6. 实板实测（COM56，固定增益 60）

```bash
# 真板：372 时间片 / 13262 帧 / 源错误 0 / 45.0 s
python -m app.live --port COM56 --duration 45 --gain-index 60   # 阶段 3 分支暂无该参数，见下
```

**诚实交代**：`--gain-index` 是功能 1 分支加的（`feat/1-wifi-check`），
本阶段分支上还没有，所以实板验证用了一个**不提交的临时脚本**直接调
`EspSdrLink.set_gain("MANUAL", 60)` + `Scheduler.run(duration_s=45)`，

**怎么读这台的结果**（不做过度解释）：

- 覆盖率 100%（8 个窗全部落在有效通带内），丢弃整窗 0 码 0 帧、源错误 0 —— 链路是干净的。
- 宽带占用 85% ⇒ 判「WiFi 压制型」。**这个房间的 2.4G 确实很忙**：
  13 个 WiFi 信道全都被 18 MHz 窗口测到 ≥50% 的宽带占用，数据区 7.2/37 个 2 MHz 栅格在动。
  这跟「仪器坏了」的形态不同（安静时 `ref_db` 只有 23，噪声底正常；
  峰值码 144–155，没有饱和到 255）。
- 因为宽带 ≥ 90%（85% 差一点），输出里已经带上「per-channel 判读没分辨力」的警示线；
  共存冲突表把 ch2–ch5 全挂到 BLE 38 上，正是「整段铺满」的典型退化形态。
- **没有在安静房间复核实板**（房间是活的，没法清场）。安静侧能力由 mock `quiet` 场景守：
  宽带 0% / 广播活动 0% / 评分 4.9。这条写在「未验证」里，不当成已验证。

## 7. 测试

```bash
cd examples/esp32c5-rf-monitor
python -m unittest tests.test_ble_risk -v   # 33 条
python -m unittest discover -s tests -t .   # 76 条（43 地基 + 33 本功能）
```

覆盖：

| 测试类 | 守什么 |
| --- | --- |
| `ScanPlanTest` | 3 个广播信道窗中心对准、数据区被覆盖、相邻窗重叠、全部落在 ISM、bins/dwell 合法、40 信道表步进（含 2426 处 4 MHz 缺口） |
| `ScenarioVerdictTest` | quiet 无风险、crowded 是密度型、两者分差 > 30、suppress 是压制型、遮挡帧有记录、命中必须是窄带、电平按信号强弱排序、`level` 中文档位 |
| `FrameHandlingTest` | 整窗 0 码丢帧、参考电平逐帧更新、覆盖率累加、远处窗不喂广播信道 |
| `PayloadTest` | 表格 4 行、结构化字段齐、可 JSON 序列化、边界文案在位、`summary` 简短 |
| `CoexistTest` | 重叠几何（full / fraction）、`wifi_busy` 判据、按风险类型给建议、广播间隔提示 |
| `PluginContractTest` | `discover("modes")` 能找到、端到端跑通、`reset()` 清空、`slice_weight == 1.0`、频段跨度 |
| `MixedScenarioTest` | `mixed` 场景两类证据同时出现时的判读 |

**踩到的坑（已在测试里固化）**：`run_scenario()` 有缓存，`test_reset_clears_everything`
直接拿缓存实例 `.reset()` 会把后面的测试连坐清空（`unittest` 按类名字母序跑，
`PluginContractTest` 在 `ScenarioVerdictTest` 之前）→ reset 测试必须自建实例。

## 8. 单射频公平性

`slice_weight = 1.0`，与 `wifi_check` / `waterfall` 相同。
（META-0087：权重悬殊会让低权重模块在共享单射频时被饿死，实测过。）

## 9. 没做的事

- 不做设备级归因（MAC/厂商/数量），任务书也没要求。
- 不做 BLE 信道跳频图的还原（需要连续 IQ，单射频分时拿不到）。
- 不做 dBm 换算（硬件只给相对功率码，换算就是编数字）。
